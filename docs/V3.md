# Outpost v3 design (draft)

Status: agreed design. Nothing here is built. The decisions taken are listed at
the end of section 14.

## 1. Goal

Every coding agent on every machine Outpost can reach works with every other
one: it can find it, message it, share files with it, and search what any of
them did before. You reach all of them from a browser or Outpost Desktop, and
what Outpost shows matches what the coding tool is actually doing.

### Non-goals

- Connections between machines. Machines and agents talk only to Outpost,
  which relays.
- Machines Outpost cannot connect to. If Outpost cannot reach a machine (for
  example behind NAT with no VPN or tunnel), it is not supported.
- Running sessions on macOS or Windows machines. Desktop local shells stay
  native PTYs.
- Agents of different accounts talking to each other.

## 2. Why v2 is muddy

- **A connection per feature.** Per-operation SSH commands with an uploaded
  Python runtime, a relay per terminal, a link per chat, a separate history
  control connection with its own socket and binding file, and signal sockets
  for events. Each has its own lifetime, retries and failure messages.
- **Root only.** Every SSH target connects as `root`.
- **One session is assumed to be one native conversation**, pinned at
  creation. After `/new` or `/resume` in a terminal, the terminal follows the
  new conversation but the registry does not, so chat reopens the original.
- **A session is frozen at creation.** Only chat instructions can change.
- **History is grouped per transcript file.** A fork shows as a second hit with
  the same messages, and compaction is not marked.
- **Local shells paste differently.** They type an image path into the PTY
  instead of pasting it.

## 3. Principles

1. **Outpost is the hub.** Outpost connects to each machine. Machines and
   agents never connect to each other or open connections to Outpost; agents
   reach Outpost only through their machine's connection.
2. **One connection per machine.** Outpost keeps one connection to each
   machine and runs that machine's node over it. Everything (operations,
   terminals, chats, files, history, events, agent tool calls) travels on it.
3. **One installed dependency.** `outpost-terminal` is the node, the terminal
   service, the chat host, the Outpost MCP server and the activity hooks, with
   the harness adapters built in. It is one TypeScript program; machines need
   only Bash and `outpost-terminal`, no Python. Outpost installs the exact
   release it needs before starting it.
4. **The machine owns its work.** Sessions, PTYs, chat hosts, native
   transcripts and session files live on the machine. Outpost never holds the
   only copy of a session's state.
5. **Outpost owns the network.** The directory, routing, delivery queues,
   channels, schedules and the history index live in Outpost.
6. **Modes differ only in authentication and authorization.** Who the users
   are, how they sign in, which credentials reach machines, and what each user
   may use. Networking, storage, limits and behavior are the same code.
7. **Outpost follows the tool.** The coding tool decides which conversation is
   current. Outpost observes and records.
8. **Configuration changes apply at a start.** A running process is never
   reconfigured in place.
9. **One agent surface.** Every agent, in a terminal or in chat, on any
   harness, gets the same Outpost MCP tools.
10. **Durable by default.** A message to an unreachable session waits in
    Outpost and is delivered once. Every request carries an idempotency key.

## 4. Domain model

```text
Account
 └─ Machine          one Linux user on one host
     └─ Session      your workstream: name, directory, harness, launch configuration
         └─ Conversation*   the tool's threads the session has used; one is current
             └─ Message*
```

| Concept | Owned by | Changes when |
| --- | --- | --- |
| Machine | Outpost | You add, rename or remove it |
| Session | The machine | You create, edit, delete or fork it |
| Conversation | The tool's native store | The tool starts, resumes, forks or compacts one |
| Message | The native store | The tool appends; Outpost never rewrites it |
| Driver | The machine | The session runs as a terminal or a chat host, one at a time |

Two rules:

- **A session has a timeline of conversations.** Any switch the tool makes
  (new, clear, resume) makes another conversation current, and terminal, chat,
  history and restarts all use the current one.
- **A conversation belongs to at most one session.** Two sessions driving one
  transcript would fork it. If one session resumes a conversation another
  session holds, the conversation moves, and the other session shows "This
  conversation moved to *X*. Choose what to resume."

## 5. Modes

| | Local | Hosted |
| --- | --- | --- |
| Users | You alone; no sign-in, loopback clients only | Accounts with sign-in, behind HTTPS |
| Credentials for machines | Your SSH config, agent and keys | A per-account SSH key |
| May use the computer Outpost runs on | Yes (Linux, WSL) | No |
| Limits | The same settings, with high defaults | The same settings, chosen by the operator |

Everything else is shared: how machines are reached, the node, storage, queues,
limits, the UI and the agent tools.

**Limits** cover, per account: machines, the history index size, channel
files, queued deliveries, schedules, and agent tool calls per minute. Reaching
one is an explicit error, never silent loss.

**When Outpost is not running** (a sleeping laptop, a restart), sessions keep
running on their machines. Agents' network tools answer "Outpost is not
reachable; try again later". Schedules do not fire and are not caught up.
History catches up when Outpost reconnects.

## 6. Machines and Linux users

A machine is **one Linux user on one host**; the user decides what a session
can do (home directory, tool credentials, file access).

- **The machine names its user.** SSH connects as that user (in local mode
  the default is your SSH config's user). Root is allowed, never required.
- **The computer Outpost runs on** is a machine whose connection is a local
  shell instead of SSH, as the user Outpost runs as. Nothing else differs.
- **System software needs an administrator.** Installing `bash` uses
  passwordless `sudo` when available (as v2 does); otherwise Outpost shows the
  exact command to run. Outpost's own software installs into the
  user's `~/.outpost`.
- **Several users on one host** are several machines, grouped by host and
  shown as `user@host`.

## 7. Sessions

| Part | Fields | Mutable |
| --- | --- | --- |
| Identity | id, machine, harness, created | Never |
| Place | project directory | Never |
| Presentation | name, handle | Any time |
| Launch configuration | environment, arguments, instructions, chat mode and model defaults | Any time; applies at the next start |
| Timeline | conversations, current one | By the tool (observed), or by you choosing one |

**Names are yours.** The session name is what you typed (or its directory) and
never changes on its own. The tool's title for the current conversation, where
the tool records one, is shown beneath it. The `@handle` used in channels
changes only when you rename the session.

**Editing.**

- Name and handle change immediately, also while the session runs.
- Launch configuration is saved as a new revision. A running driver records
  the revision it started with; when they differ, the session shows "Changes
  apply at the next start" with **Restart now**, which stops it and starts it
  again in the same conversation. Nothing restarts unless you ask.
- An edit names the revision it was based on; a concurrent edit is refused with
  "This session changed; review the new settings."
- Harness and directory cannot change. Native stores key conversations by
  directory, so moving is a fork: **Continue in another directory** creates a
  new session whose first conversation is forked from the current one.

## 8. Following the tool's conversations

The node observes switches through each harness's hooks in terminals (as v2's
activity observer does) and through ACP in chat. Each switch updates the
session's timeline, so terminal restarts, chat, history and the UI open the
current conversation. Earlier conversations stay listed under the session;
choosing one makes it current and resumes it. "New conversation" in chat is
the same switch as `/new` in a terminal.

## 9. History across conversations

History understands how conversations relate, so results are neither
duplicated nor missing.

**Message identity.** Each harness adapter gives every message a logical
identity: the tool's own message ID where its store has one (Claude Code
`uuid`, Codex item identity), otherwise one derived from the message content
and its parent's identity. The index stores a logical message once and records
every conversation that contains it.

**Lineage.** A conversation whose leading messages share identities with
another is its fork at the first difference. Fork metadata the tool records
(Codex `forked_from_id`) and Outpost's own fork action take precedence over
detection. Lineage edges can cross Outpost sessions.

**Compaction.** A compaction is a boundary inside one conversation. The adapter
marks it where the tool records it (Claude Code's compact boundary and summary,
Codex `compacted` items). Summaries are indexed as kind `summary` and excluded
from search by default, because they repeat indexed content. They are searched
when the original messages are gone from the store.

**What the tools return.**

- `search_history` returns each logical message once, attributed to the
  conversation where it first appeared, with "also in" listing the forks that
  contain it and their Outpost sessions. Results before a compaction say
  "before a compaction; the agent now has only a summary". Grouping by session
  uses Outpost sessions across their whole timeline.
- `read_context` reads along one conversation. At a fork point it lists the
  other branches; at a compaction boundary it shows the summary and continues
  into the messages before it.
- `get_session` returns the Outpost session, its timeline, and the lineage of
  the conversation asked about.

**Keeping it maintainable.** Native store formats are undocumented and change
between tool versions. Each adapter's identity and boundary reading is covered
by fixture transcripts recorded from real tool versions, and an unrecognized
record degrades to "no identity" (content-derived) instead of failing the
index.

## 10. Terminals: one contract, two hosts

| Capability | Managed session | Desktop local shell |
| --- | --- | --- |
| Input, resize, output, search, clear, links, bell, OSC 52 copy | yes | yes |
| Paste text with the program's bracketed-paste mode | yes | yes |
| Paste or drop an image or file | stored on the machine, reference pasted | stored on your computer, reference pasted |
| Persistent across disconnect | yes | no |
| Activity, session files, Outpost MCP, messages | yes | no |

- **Pasting is the emulator's job.** For local shells the desktop renderer is
  the emulator, so an image reference goes through its paste path, which
  applies bracketed paste. v2 types it into the PTY instead.
- **A local shell does not know where its program runs.** After `ssh` in a
  local tab, a pasted path names a file on your computer; the notice says
  "Image saved on this computer".
- **For everything in the managed column**, open a managed session on the
  computer Outpost runs on (Linux, WSL).

## 11. The node

`outpost-terminal node` runs on the machine for as long as Outpost's connection
to it is open, and speaks the node protocol over that connection's stdin and
stdout. When the connection drops, the node exits and Outpost reconnects. It
replaces the per-operation runtime upload, the terminal and chat relays, the
history bridge and the signal sockets.

- **Sessions:** the registry (identity, presentation, launch revisions,
  timeline), creation, editing, deletion and forking.
- **Drivers:** starts and supervises terminal services and chat hosts, which
  keep running when the connection ends, as today.
- **Observation:** conversation switches, titles and activity, sent as events.
- **Files and history:** the session file store; reading native stores and
  sending new history records from a checkpoint Outpost acknowledges.
- **Local endpoint:** a private Unix socket for the Outpost MCP and the
  `outpost` CLI in sessions. Local tools are answered by the node; network
  tools go to Outpost over the connection. When the connection is down, they
  fail at once with "Outpost is not reachable".

**Harness adapters are TypeScript**, part of `outpost-terminal`. Phases 1 and
2 change today's Python adapters; phase 3 ports them together with the
runtime, the activity hooks and the MCP server, so the node never runs Python.

## 12. The node protocol

Length-prefixed frames, as today's relay framing; control frames are JSON:

| Frame | Direction | Use |
| --- | --- | --- |
| `call {id, op, args, key}` / `result {id, ok, data \| error}` | both | Request and response; `key` makes retries safe |
| `open {stream, kind, args}` / `data` / `close {stream, reason}` | both | Streams with per-stream credit flow control |
| `event {kind, data}` | node → Outpost | Activity, conversation switched, title changed, file added, session changed |
| `ping` / `pong` | both | Liveness |

Streams: `terminal` (today's relay protocol), `chat` (today's chat host
protocol), `file` (chunked, final hash), `history` (records from an
acknowledged checkpoint).

Node operations: `sessions.list|create|update|delete|fork|terminate|restart`,
`sessions.switch`, `software.inspect|install`, `directories.suggest`,
`conversations.search`, `files.list|remove|read|receive`. Outpost operation for
agents: `mcp.call {session, tool, arguments}`; Outpost checks that the session
belongs to the machine whose connection carried the call.

**Versions always match.** Outpost installs the release it needs before
starting the node, as it installs Outpost Terminal today, and refuses a node
that reports another protocol. There is no negotiation and no handling of older
nodes.

## 13. The agent surface

Every launch gets the same Outpost MCP server (as `outpost_mcp_servers.servers`
provides in v2), backed by the node's local endpoint:

| Tool | Answered by | Purpose |
| --- | --- | --- |
| `publish_file` | node | Share a file with the user and channel members |
| `list_machines`, `list_sessions` | Outpost | Machines and sessions with state and the tool's current title |
| `message_session` | Outpost | Deliver a message to any session; its reply returns later |
| `fetch_file` | Outpost, via both nodes | Copy another session's shared file into this session |
| `search_history`, `read_context`, `read_message`, `get_session` | Outpost's index | Search and read any machine's history |
| `post_to_channel` | Outpost | Post to a channel the session belongs to |

### Delivering messages

A message to a session (from another agent, a channel or a schedule) reaches
it through the best path its driver and harness offer:

| Driver | Harness | Delivery |
| --- | --- | --- |
| Chat | any | A queued ACP prompt, as today |
| Terminal | Claude Code | Native: the Outpost MCP server is a Claude Code [channel](https://code.claude.com/docs/en/channels-reference). The message arrives as a `<channel>` event, queued by Claude Code while it is busy and handled on its next turn. |
| Terminal | others, or Claude Code without channels | Guarded typing (below) |

**Guarded typing**, after [herdr](https://herdr.dev/)'s `terminal.send`:

- Only while the agent is idle, as its activity hooks report. A waiting or
  working agent's messages stay queued.
- Only after you have sent or cleared your draft, or after about 3 seconds
  without your typing; keys you press during delivery are held and delivered
  after it.
- The message is pasted (with the program's bracketed-paste mode) and followed
  by Enter, wrapped as `[Outpost: from @sender]` so the agent knows its origin.
- Each session can turn automatic delivery off. Then messages are shown
  ("2 messages waiting") and delivered when you choose **Deliver now** or the
  session next runs in chat.

**Claude Code channels are a research preview.** A channel outside Anthropic's
allowlist loads only with `--dangerously-load-development-channels`, which
shows a confirmation at startup, and Team and Enterprise admins must enable
channels. The adapter uses the channel path only when the session's Claude Code
accepted it (the node sees the channel registered) and falls back to guarded
typing otherwise.

## 14. Phases

Each phase ships a working product.

1. **Users and paste.** Machines name their Linux user; local shell image paste
   goes through the renderer's paste path.
2. **Sessions.** The conversation timeline in the registry (chat follows `/new`
   and `/resume`), the tool's title under the name, rename, and launch
   configuration editing with revisions.
3. **The node.** One connection per machine running `outpost-terminal node`,
   with the runtime, harness adapters, activity hooks and MCP server ported to
   TypeScript. Delete the runtime upload, relays, history bridge, signal
   sockets and the Python requirement.
4. **History.** Message identity, lineage, fork and compaction boundaries, and
   the result shapes in section 9, built once in the TypeScript adapters.
5. **One agent surface.** The local endpoint, the tools in section 13 for every
   session, message delivery into terminal sessions, and the shared limits.

Phases 1 and 2 are small changes on today's code. Phase 3 changes how
everything travels without changing what users see; it is the largest step.

### Decisions

| Decision | Choice |
| --- | --- |
| Harness adapters | TypeScript, part of `outpost-terminal`; machines need no Python |
| Session names | Always yours; the tool's title is shown beneath |
| A conversation resumed by another session | Moves; the old session asks what to resume |
| Editing the directory | Not allowed; continue in another directory as a fork |
| History | Message identity and lineage, with fork and compaction boundaries |
| Messages into terminal sessions | Native where the tool offers it (Claude Code channels), guarded typing otherwise; per-session opt-out |
