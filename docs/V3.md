# Outpost v3 connectivity

**Accepted design · 22 November 2026**

Each remote Linux machine enrolls with one Outpost server under one execution account. The enrollment selects **one connection method**. Both methods run the same `outpost-terminal` machine service and carry the same bidirectional Outpost protocol.

The machine owns the coding agent and its sessions. Browser and Desktop clients attach through their local or hosted Outpost instance, which owns the workspace and authorizes access.

[Machine setup and removal](../README.md#machine-setup-and-removal)

## Choosing a connection method

**Machines → Add a machine** defaults to **Connect over SSH**. Choose it when the Outpost instance can authenticate to the target execution account and run a command, directly or through an approved SSH bastion. Otherwise, an operator can choose **Run setup on the machine** and explicitly enable a persistent outbound connection. Outbound access is off by default.

| Add a machine choice | Local tool | Hosted service |
| --- | --- | --- |
| **Connect over SSH** | Outpost opens SSH from the computer running the local tool, using its OpenSSH configuration, keys and any configured jump host. | The hosted server opens SSH using the owner's account-scoped SSH credentials and a route available to that server. |
| **Run setup on the machine** | The machine needs a reachable address for the local instance. A loopback-only workstation is unreachable from a remote machine by default. | The machine connects out to the hosted server. A client and a machine behind different NATs can both reach the same public Outpost server this way. |

Enrollment treats reachability as stable. An operator whose laptop alone can use a bastion can run Outpost on that laptop. If neither direction is reachable and permitted, Outpost reports the machine as unreachable.

Outpost records the selected method and uses it for every reconnect. An SSH failure surfaces the SSH error. A dropped outbound connection reconnects to the same server. Changing methods requires explicit enrollment.

## Connect over SSH

1. **First connection.** Outpost checks the target platform and installed versions. It transfers the matching machine service and its release checksum over SSH, verifies the build, and installs it atomically. It reuses installed coding tools and provisions the selected tools and their required adapters when missing. Setup can be retried after interruption. A restricted target can receive the required artifacts over the SSH path, including an ACP adapter. The agent's access to its model provider is a separate requirement.
2. **Subsequent connections.** Outpost runs `outpost-terminal node` as a remote command using `ssh -T`. SSH provides encrypted stdin and stdout. `-T` keeps the connection to the node free of terminal processing. The machine service allocates a PTY for an interactive coding tool and keeps the agent running independently of SSH. A compatible service can immediately list, create or reattach to sessions.

These operations use the SSH command's byte stream. A bastion can forward SSH to the target. Outpost needs neither an application port forward (`-L` or `-R`) nor an HTTPS listener on the machine. An SSH-enrolled service initiates zero connections to Outpost, including when SSH is interrupted.

## Run setup on the machine

When Outpost cannot make even the first SSH connection, the machine page supplies a one-time `curl` installation command. An operator runs it through an existing shell, a bastion, a console or their provisioning system. Running the command is the opt-in to ongoing outbound access.

The command fetches the installer from the intended Outpost server and verifies and installs the same machine service. Before redeeming the short-lived code, the service saves its own random credential locally. The code authorizes one machine enrollment for its workspace owner. If the reply is lost, the machine can complete that enrollment with the same credential. The installed service survives logout, starts after a reboot, and reconnects to that server using its credential.

The machine opens an authenticated, encrypted connection to the server. Outpost sends work over that connection, and the machine sends results and events back on it. The enrollment authorizes Outpost operations on that machine only. Revoking the enrollment closes its active link and prevents reconnection.

## What the connection carries

The Outpost machine protocol multiplexes framed control messages and numbered data streams over either connection. Each attachment is authorized for its owner, machine and session. Transferring a machine to a new owner or server requires releasing its local enrollment. SSH account access and keys are managed separately.

| Operation | Behavior on both methods |
| --- | --- |
| Sessions and terminals | List sessions by their stable IDs. Create one or reattach to the running agent and restore its terminal state. A disconnect detaches the viewer and leaves the agent running. Uncertain keystrokes and pastes require a fresh user action. |
| Image paste and published files | Upload image bytes in bounded chunks, then paste the confirmed machine-local reference. An agent can use the Outpost MCP tool `publish_file` while the client is away. The machine stores the file, notifies attached viewers and serves the bytes when requested, including after reattachment. |
| Chat and ACP | Chat can send prompts, stream updates and resolve approvals over either method. The persistent chat host speaks the Agent Client Protocol (ACP) over local stdio to a coding tool or its adapter. A reconnecting viewer can recover the journal and pending approvals. [Session and Chat behavior](CHAT.md) |
| Channels, session messages and schedules | The Outpost instance coordinates delivery. It must be running and able to reach each recipient when delivery is due. Hosted Outpost can open SSH for a scheduled prompt while the user's laptop is asleep. A local scheduler needs its own computer awake. A failed delivery reports unavailability. |

## Acceptance criteria

- Enroll a clean Linux target through an SSH bastion in local and hosted mode using credentials available to the respective Outpost instance. With target egress blocked, install the machine service and a selected tool from available artifacts. Drop SSH and reattach to the same running agent. Observe zero machine-initiated Outpost connections.
- With inbound access blocked at both client and target, enroll from a shell on the target and attach through a reachable hosted server. Drop the enrollment response and retry with the same credential. Verify rejection of attempts to claim a redeemed code with another credential, expired codes for new enrollments, and revoked machine credentials. Check reconnect after a link loss and service startup after a reboot.
- Repeat the same session and transfer checks over both methods. Paste an image, retrieve an agent-published file byte-for-byte after disconnecting, and reconnect to an outstanding ACP approval. The turn receives one approval and the agent process survives the connection loss.
- Deliver a channel mention and a scheduled prompt over each method with the interactive client closed. Then interrupt the selected method and verify that Outpost reports the delivery outcome and preserves the enrollment choice.
